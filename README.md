# GitHub Actions Workflow Chaining Example

This repository demonstrates a solution to a common GitHub Actions challenge: **triggering a workflow after another workflow has pushed changes to a Pull Request**.

## 🎯 The Problem

GitHub Actions doesn't allow re-triggering a workflow on a PR when one of the steps in that workflow pushes additional changes (like linter fixes or auto-generated files). This limitation exists because:

1. The `GITHUB_TOKEN` has limited visibility to prevent circular dependencies
2. GitHub prevents infinite workflow loops
3. Workflows triggered by `GITHUB_TOKEN` won't trigger other workflows

This creates a challenge when you want to:
- Auto-generate files based on source changes
- Run CI validation on those generated files
- Keep generated files in sync with source files

## ✨ The Solution

This repository uses **workflow chaining** with the `workflow_run` trigger to solve this problem:

1. **Workflow 1 (Generate Files)**: Triggers on PR events, generates files, and commits them
2. **Workflow 2 (CI)**: Triggers when Workflow 1 completes, validates the generated files

The key is using `workflow_run` instead of typical PR triggers for the validation workflow.

## 🔄 How It Works

### Workflow 1: Generate Files

**Trigger**: Pull Request events (opened, reopened, synchronize) or push to main
**Purpose**: Generate files with MD5 checksums in filenames

```yaml
on:
  pull_request:
    types: [opened, reopened, synchronize]
    paths:
      - 'sources/**'
  push:
    branches:
      - main
    paths:
      - 'sources/**'
```

**Process**:
1. Checks out the repository
2. For each file in `sources/`:
   - Calculates MD5 hash of the content
   - Creates a copy in `generated/` with format: `{basename}_{md5hash}.md`
3. Commits and pushes the generated files back to the branch
4. Uses `[skip ci]` in commit message to prevent infinite loops

**Example Output**:
- `sources/document1.md` → `generated/document1_a1b2c3d4e5f6...md`

### Workflow 2: CI Validation

**Trigger**: Completion of the "Generate Files" workflow

```yaml
on:
  workflow_run:
    workflows: ["Generate Files"]
    types:
      - completed
```

**Process**:
1. Reports commit status as "pending" to the PR
2. Checks out the branch from the completed workflow run
3. Validates each file in `generated/`:
   - Extracts MD5 hash from filename
   - Calculates actual MD5 hash of file content
   - Compares the two hashes
4. Checks correspondence between source and generated files
5. Reports validation results
6. Updates commit status to "success" or "failure"

**Important Note**: Workflows triggered by `workflow_run` don't automatically appear in PR checks. We use the GitHub API (`actions/github-script`) to explicitly report the commit status back to the PR, making the CI results visible in the PR's status checks.

**Validation Checks**:
- ✅ MD5 hash in filename matches actual file content
- ✅ Each source file has a corresponding generated file
- ⚠️ Detects orphaned generated files (no corresponding source)

## 🚀 Usage

### Setting Up

1. Clone this repository:
   ```bash
   git clone <repository-url>
   cd workflow-run-gha-example
   ```

2. The workflows are already configured and ready to use

### Testing the Workflow

#### Option 1: Create a Pull Request

1. Create a new branch:
   ```bash
   git checkout -b test-branch
   ```

2. Modify a source file:
   ```bash
   echo "# New Content" >> sources/document1.md
   git add sources/document1.md
   git commit -m "Update document1"
   git push origin test-branch
   ```

3. Create a Pull Request on GitHub

4. Watch the workflows:
   - **Generate Files** workflow runs first and commits generated files
   - **CI** workflow runs automatically after completion and validates checksums

#### Option 2: Push to Main

1. Make changes to source files:
   ```bash
   echo "# New Section" >> sources/document2.md
   git add sources/document2.md
   git commit -m "Add new section"
   git push origin main
   ```

2. Both workflows will run in sequence

### Monitoring Workflow Execution

Navigate to the **Actions** tab in your GitHub repository to see:
- Workflow execution history
- Detailed logs for each step
- Validation results and summaries

## 🛠️ Configuration

### Generate Files Workflow

**Key Settings**:
```yaml
permissions:
  contents: write        # Required to push changes
  pull-requests: write   # Required for PR operations
```

**Commit Message**:
- Uses `[skip ci]` to prevent re-triggering itself
- Identifies commits as bot-generated

### CI Workflow

**Key Settings**:
```yaml
if: ${{ github.event.workflow_run.conclusion == 'success' }}
permissions:
  statuses: write   # Required to post commit status to PR
  contents: read    # Required to checkout repository
```
- Only runs if the Generate Files workflow succeeded
- Checks out the correct branch using `github.event.workflow_run.head_branch`
- Uses `statuses: write` permission to post commit status back to the PR

## 📝 Customization

### Changing Hash Algorithm

To use a different hash algorithm (e.g., SHA256), update the scripts:

1. In `.github/scripts/generate-files.sh`:
   ```bash
   sha256_hash=$(sha256sum "$source_file" | awk '{print $1}')
   ```

2. In `.github/scripts/validate-checksums.sh` and `.github/scripts/check-correspondence.sh`:
   ```bash
   actual_hash=$(sha256sum "$generated_file" | awk '{print $1}')
   ```

3. Update regex patterns to match SHA256 (64 hex characters instead of 32)

### Adding More File Types

Modify the pattern in the relevant scripts:

In `.github/scripts/generate-files.sh`:
```bash
for source_file in sources/*.{md,txt,json}; do
```

In `.github/scripts/check-correspondence.sh`:
```bash
for source_file in sources/*.{md,txt,json}; do
```

### Customizing Triggers

Add more trigger events to `generate-files.yml`:
```yaml
on:
  pull_request:
    types: [opened, reopened, synchronize, labeled]
  push:
    branches:
      - main
      - develop
```

## 🔐 Security Considerations

1. **Token Permissions**: The workflows use `GITHUB_TOKEN` with minimal required permissions
2. **Branch Protection**: Consider enabling branch protection rules
3. **Workflow Approval**: For public repos, require approval for first-time contributors
4. **Skip CI**: The `[skip ci]` flag prevents infinite loops

## 🐛 Troubleshooting

### CI Status Not Showing in PR

**Problem**: CI workflow runs but doesn't appear in PR checks

**Solution**: This is the expected behavior for `workflow_run` triggered workflows. The fix is already implemented using `actions/github-script` to post commit statuses. The workflow explicitly reports its status using the GitHub API:

```yaml
- name: Report CI status as pending
  uses: actions/github-script@v7
  with:
    script: |
      github.rest.repos.createCommitStatus({
        sha: '${{ github.event.workflow_run.head_sha }}',
        state: 'pending',
        context: 'CI / validate'
      })
```

This creates a visible check in the PR with the status of the CI validation.

### Workflow Not Triggering

**Problem**: CI workflow doesn't run after Generate Files completes

**Solutions**:
- Ensure workflow names match exactly in the `workflow_run` trigger
- Check that Generate Files workflow completed successfully
- Verify branch protection rules aren't blocking workflow runs

### Permission Errors

**Problem**: Workflow can't push changes

**Solutions**:
- Add `contents: write` permission to the job
- Check repository settings for Actions permissions
- Ensure `GITHUB_TOKEN` has proper access

### Generated Files Not Updating

**Problem**: Generated files are stale or missing

**Solutions**:
- Check the workflow logs for errors
- Verify the `sources/` path filter in the trigger
- Ensure file patterns match your source files
